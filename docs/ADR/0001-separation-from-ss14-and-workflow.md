# ADR-0001. Отделение от SS14 и модель работы над Build

Дата: 2026-11-18. Статус: **принято** (владелец проекта, 18.11.2026).

## Контекст

Build начинался как перенос механик и данных Space Station 14 на Astrocore Engine. Контент
(`content/prototypes`, карты, спрайты) генерировался Python-скриптами из локального клона SS14 и
форка NightCity и был помечен «не править руками»: источником правды оставался чужой репозиторий.
В `content/prototypes/ss14` лежит всё дерево сущностей SS14 (10 540 прототипов), большая часть —
без механик. Игровой код — один крейт `gameplay` с общим `State` (сотни полей, `module.rs` на
9 300 строк), поэтому систему нельзя отключить или заменить, не правя ядро. Документ Build
(Notion) обещает нейтральную базу с независимыми модулями, которую тематические проекты
форкают; код этому не соответствовал.

## Решение

1. **Источник правды — Build.** Данные, взятые из SS14, становятся нашими: `content/` правится
   руками, генераторы — одноразовые инструменты импорта (`scripts/`, позже `tools/legacy`), их
   результат после импорта не перезаписывается автоматически. SS14 — референс поведения и
   архив данных, не зависимость.
2. **Свой формат.** Логика — Rust, данные — RON (прототипы с наследованием `parents`/`abstract`,
   карты Build). Совместимость с YAML SS14 не цель; импорт YAML остаётся инструментом.
3. **Только то, что работает.** В репозитории держим прототипы, у которых есть механика или
   которые нужны картам; остальные узлы дерева SS14 уходят из `content/` (импорт по запросу).
   Пространство имён движка `ss14:` будет заменено своим (отдельный шаг с миграцией карт).
4. **Игровые системы независимы.** Каждая механика — система (`GameSystem`, `crates/gameplay/src/systems`):
   своё состояние, свои команды клиента, свой тик, свой реплицируемый вид. Общее состояние мира
   (персонажи, предметы, должности) — `State`, система получает его по ссылке. Систему можно
   отключить (`GameplayModule::without_system`) или заменить своей (`with_system`) — это и есть
   точка расширения для форков. Перенос существующих механик из `State` в системы идёт по одной,
   с зелёными тестами на каждом шаге.
5. **Нейтральность.** Карта по умолчанию — нейтральная (из ванильного SS14 или своя), тематический
   контент (NightCity и т. п.) — в форках.
6. **Лицензии.** Исходные лицензии и авторство данных SS14 и форков сохраняются
   (`assets/ss14/LICENSE-ASSETS.md`, `meta.json`). Код Build, как и движка, — `AGPL-3.0-or-later`
   (решение владельца, 19.11.2026; прежде Build был под MIT).

## Модель работы

* **Программист механик:** новая механика — система в `systems/` по шаблону (компоненты
  прототипа → серверная логика → реплицируемый вид → интерфейс → тесты на тестовом стенде
  сервера). Ветка → PR → CI (fmt, clippy `-D warnings`, тесты, сборка сервера без графики) → ревью.
* **Контент-дизайнер:** правит RON без Rust: наследует базовый прототип и переопределяет поля.
  Проверка — валидатор контента с понятными ошибками (будет), перезагрузка контента без
  перекомпиляции (будет).
* **Маппер:** строит карту в игре (админ-инструменты, вид сверху) или в Studio движка, сохраняет
  в RON; валидатор карты проверяет герметичность, точки появления, должности.
* **Художник:** спрайты в формате RSI (`meta.json` с лицензией и автором), манифест рендера
  собирается автоматически.
* **Плейтест:** `scripts/run_all` (локальный сервер с админ-правами), консоль, issue с шагами.
* **Процесс:** в `main` — только через PR; ИИ-агенты работают так же. Решения — `docs/ADR`,
  факты — `docs/PROGRESS.md`, бэклог — issues. README — короткая точка входа, остальное — `docs/`.
* **Форк:** берёт Build, отключает или заменяет системы, кладёт свой контент поверх, тянет
  исправления из upstream.

## Порядок работ

1. Каркас систем и перенос изолированных механик (чат, консоль) — начато этим ADR.
2. Перенос остальных систем из `State` (лобби, химия, атмос, питание, бой…), разрезание `module.rs`.
3. Схемы компонентов RON, валидатор контента, перезагрузка контента.
4. Чистка `content/` от узлов без механик, своё пространство имён, нейтральная карта по умолчанию.
5. Админ-маппинг с сохранением карт в RON; документы «как сделать X», шаблоны PR и issue.
6. Стенд скриншотов для визуальных проверок.

## Последствия

* Обновления SS14 больше не подтягиваются автоматически; перенос новых механик — осознанная задача.
* Генераторы перестают быть обязательной частью сборки контента.
* Пока системы переносятся, часть механик живёт в `State`, часть — в `systems/`; граница описана
  в `docs/SYSTEMS.md`.
