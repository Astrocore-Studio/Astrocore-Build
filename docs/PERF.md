# Замеры производительности

Цель — 160+ игроков на сервер: такт симуляции укладывается в 33 мс (30 Гц). Каждая фаза плана
заканчивается замером; сюда записываются команда, машина и результат.

## Фаза 1. Ядро сущностей

Дата: 2026-11-26. Engine `fd91033`. Машина: 4 ядра, 15 ГБ, Linux, сборка `--release`.

```bash
cargo run --release -p astrocore-map --example bench_core -- ../reference/space-station-14/Resources/Prototypes
```

| Замер | Результат |
|---|---|
| Загрузка и наследование всех прототипов SS14 (2209 файлов, 10 122 прототипа сущностей) | 0,5 с |
| Грид 256×256 тайлов | 4 мс |
| Создание 20 000 сущностей из прототипов на гриде | 61 мс (3,1 мкс на сущность) |
| Такт с 200 движущимися игроками и 10 подписчиками на `MoveEvent` | 62 мкс в среднем, 168 мкс худший |

В замере нет сети, физики, атмосферы и игровых систем: он показывает, что хранилище сущностей,
события и иерархия занимают меньше 1 % бюджета такта. Замеры с сетью и ботами появятся
в фазе 2 (задачи 2.2 и 8.2).

## Фаза 2. Сеть

Дата: 2026-11-26. Engine `df86f21`. Та же машина (4 ядра).

```bash
cargo run --release -p astrocore-net --example bench_net -- 200 20000 300
```

Сервер без клиентских миров: 200 условных игроков ходят по гриду 256×256 с 20 000 сущностей,
каждый такт меняется 1 % сущностей, клиенты подтверждают каждое состояние.

| Замер | Результат |
|---|---|
| Такт сервера с PVS и сборкой состояний, 200 игроков | 6,1 мс в среднем, 11 мс худший (бюджет 33 мс) |
| То же, 50 игроков | 1,7 мс |
| Трафик в игре | 14 КБ/с на игрока (цель — не больше 30) |
| Вход в игру | 585 КБ на игрока: в основном тайлы грида 256×256 без сжатия |

Первая версия учёта «что знает клиент» на хеш-таблицах давала 21 мс на такт; массивы по индексу
сущности дали 6,1 мс. Что ещё можно ускорить: сжатие больших состояний (вход в игру), повторное
использование закодированных состояний сущности для игроков с одинаковой базой.

В замере нет физики и игровых систем. Физика считает только бодрствующие тела: стены и лежащие
предметы в расчёт не входят.

## Фаза 2. Сеть после сжатия состояний и слоёв видимости

Дата: 2026-11-26. Engine `bbb6a7d`. Та же машина, та же команда `bench_net -- 200 20000 300`,
три прогона.

| Замер | Было | Стало |
|---|---|---|
| Вход в игру, на игрока | 585 КБ | 43 КБ |
| Трафик в игре, на игрока | 14 КБ/с | 12 КБ/с |
| Такт сервера, 200 игроков, в среднем | 6,1 мс | 6,7–7,2 мс |
| Такт сервера, худший | 11 мс | 12–21 мс (такты одновременного входа всех 200 игроков) |
| Такт сервера, 50 игроков | 1,7 мс | 2,0 мс |

Рост среднего такта — цена сжатия (LZ4), проверки слоёв видимости и проверки перехода между
гридами при каждом движении. Бюджет такта — 33 мс.

## Фаза 5. Взрыв на Saltern

Дата: 2026-11-27. Пример `check_explosion` (взрыв `Default` силой 2000, наклон 5, предел 100 у
точки появления опоздавших). Та же машина, сборка release.

| Замер | Результат |
|---|---|
| Площадь взрыва | 79–84 клетки |
| Обработка | 2 такта, 44–51 мс всего |
| Худший такт взрыва | 30–34 мс |
| Ранено / удалено сущностей | ~125 / 24 |
| Полная пересборка сетей узлов (кабели, трубы) | ~19 мс |

Взрыв меньше `explosion.single_tick_area_limit` (400 клеток) обрабатывается за один такт без
учёта `explosion.max_tick_time`, как в SS14, поэтому такт выходит выше бюджета 7 мс. На время
взрыва сети узлов не пересобираются (`explosion.node_sleep`), но после взрыва их пересборка
полная: каждая разорванная сеть пересчитывается целиком. Тот же скачок даёт перерезанный кабель.
Долг: пересобирать только затронутые сети (как `NodeGroupSystem` SS14) — к фазе 8 (замеры со
160 игроками).
