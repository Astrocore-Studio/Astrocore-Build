# Промпт для продолжения работы: перенос контента SS14 в Astrocore Build

Ты продолжаешь работу над **Astrocore Build** — нейтральной базовой игрой, которая **точно переносит механики Space Station 14** на движок Astrocore (Rust, Bevy 0.20, сервер авторитетный). Ничего не придумывай сама: каждую механику сначала найди в исходниках SS14 и повтори их поведение и числа. Если в исходниках чего-то нет или в билде нет нужной системы, скажи об этом прямо, а не пропускай молча.

## Репозитории и пути
- Рабочий репозиторий Windows: `D:\projects\astrocore\Astrocore-Build` (GitHub `Astrocore-Studio/Astrocore-Build`, ветка `main`). Движок отдельно: `D:\projects\astrocore\Astrocore-Engine`. Логику и контент помещать в Build, общие возможности — в Engine.
- Исходники SS14 только для чтения: `D:\projects\space-station-14`. Текущий снимок для новых переносов: `31f782a809851c674bd8f86c3aca7c381118c539`. C# — `Content.Shared/`, `Content.Server/`, `Content.Client/`; данные и ресурсы — `Resources/`.
- Сборка и запуск — нативные Windows EXE через PowerShell. WSL не использовать. Инструменты, кэш, временные карты, логи и снимки хранить в Build `.local` на D:.

## Жёсткие правила
1. Перед коммитом: `cargo fmt --all`, `cargo clippy --workspace --all-targets` без единого предупреждения, `cargo test -q --workspace` зелёный.
2. Сервер авторитетный: клиент только шлёт команды (`CMD_*` в `crates/gameplay/src/wire.rs`) и рисует то, что реплицировано.
3. Не закрывай пробелы словами «не перенесено» и не пропускай. Если перенести нельзя (нет системы), скажи честно и перечисли.
4. Звуки и спрайты берутся только из SS14. **2026-11-15 владелец ответил «можно все» и разрешил перенос всех исходных ассетов, включая NC и Custom.** Повторное разрешение по отдельной лицензии не требуется. Сохранять исходные лицензии, авторство и ссылки на источники; разрешение на перенос в проект не меняет лицензию ресурса.
5. Временные правки карты и отладочные файлы не коммитить.
6. Содержимое генерируется скриптами из SS14: не правь `content/prototypes/*.ron` вручную, правь генератор и запускай его заново.

## Устройство проекта
- `crates/gameplay/src/` — игровая логика: `module.rs` (главное состояние `State`, тик, команды), `handlers.rs` (цепочка `InteractionHandler`), `wire.rs` (команды, регистрация реплицируемых компонентов), `body.rs` (тело, метаболизм, температура, статусы), `chem.rs` (реагенты, реакции), `health.rs`, `reagents.rs` (`Solution`), `chemlab.rs` (смесители, плитка, ХимМастер), `cryo.rs`, `defib.rs`, `fx.rs` (подсказки и звуки), `dispenser.rs`, `analyzer.rs`, `idconsole.rs`, `electric.rs`, `piping.rs`, `tests.rs` (интеграционные тесты).
- `crates/atmos` — газы и трубы (`pipes.rs`: насосы, вентили, фильтр, термомашины, баллоны, криокапсула).
- `crates/tools` — `import-map` (карта SS14 → наш формат) и `sync-sprites`.
- `apps/client` — клиент (Bevy + egui): `hud.rs` окна, `lib.rs` системы, `sounds.rs`, `statusfx.rs`, `lights.rs`. `apps/server` — сервер.
- `content/prototypes/*.ron` — **сгенерированное** содержимое. `assets/ss14/` — текстуры, звуки, `render-manifest.json`.
- `scripts/` — генераторы: `gen_items.py` (предметы), `gen_chem.py` (реагенты, реакции, статусы), `gen_chem_machines.py`, `gen_spawners.py` (шкафы, раздатчики), `gen_vending.py`, `gen_roles.py`, `gen_computers.py`, `gen_access.py`, `sync_audio.py`, общий загрузчик `ss14yaml.py`.

## Рабочий цикл переноса механики
1. Найти в SS14 прототип (YAML) и систему (C#): прочитай **исходник**, а не пересказ.
2. Если данные берутся из прототипов, расширь соответствующий генератор и перегенерируй `content/prototypes/*.ron`; прочитай результат глазами.
3. Реализуй в `gameplay` (состояние в `State`, разбор прототипа при создании, команды в `wire.rs`, обработчик в `handlers.rs`, окно в `apps/client/src/hud.rs`).
4. Добавь тест: интеграционный в `crates/gameplay/src/tests.rs` (есть `harness`, `command`, `spawn`, хелперы `peek`, `lab_view`, `cryo_view`) и/или модульный рядом с кодом.
5. Спрайты и звуки: добавь пути в sparse-checkout SS14, запусти `cargo run -q -p tools --bin sync-sprites -- <SS14>/Resources/Textures`, `python3 scripts/sync_audio.py <SS14>` и `cargo run -q -p server -- --write-manifest assets/ss14/render-manifest.json`.
6. Раздел в `README.md`, коммит, пуш.

## Команды
- Основной запуск Windows: `.\scripts\run_saltern.ps1 -LocalEngine -GraphicsBackend Vulkan -ClientArguments '--no-shadows'`. Для актуализации существующего импорта — `-Reimport`. Локальный Engine подключается через отдельный `.local/dev/Cargo.toml`; закреплённые зависимости основного Build не подменяются.
- Проверки Windows: `. .\scripts\_dev_env.ps1`, затем `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test -q --workspace`. Интеграционные сценарии добавлять в существующий `crates/gameplay/src/tests.rs`.
- Снимки живого Windows-клиента: `-Mode Smoke` использует существующие `--autoplay`/`ASTRO_SHOT` и кадры 260/340. `-LogName` разделяет журналы нескольких клиентов. Временную карту и исходный импорт хранить раздельно.
- Следующие bash/xvfb-команды — историческая запись прежнего Linux-окружения; на этой машине использовать Windows-команды выше.
- Импорт карты: `cargo run -q -p tools --bin import-map -- <SS14>/Resources/Maps/saltern.yml /tmp/saltern.ron Saltern`.
- Сервер: `bash scripts/run_server.sh --map /tmp/saltern.ron`; клиент: `bash scripts/run_client.sh --autoplay`. Без экрана: `xvfb-run -a …`. Для снимков окна: `ASTRO_SHOT=<каталог>` (кадры 260 и 340), `ASTRO_OPEN_ID=<hex id объекта>` открывает окно машины; `ASTRO_MAP=<карта>` нужен и клиенту. Идентификаторы объектов карты: `0x10000000 + индекс в списке items`.
- Генераторы запускаются из корня репозитория: `python3 scripts/gen_chem.py <SS14>`, `python3 scripts/gen_items.py <SS14> <SS14>/Resources/Maps/saltern.yml`, `PYTHONPATH=scripts python3 scripts/gen_chem_machines.py <SS14>`.

## Подводные камни
- Команды дольше 2 минут уходят в фон; долгие задачи запускай фоном и проверяй вывод.
- Место на диске ограничено: каталог `target` легко разрастается (десятки ГБ). При нехватке места удали старые тестовые бинарники в `target/debug/deps` и `target/debug/incremental`.
- В sparse-checkout SS14 добавляются **файлы по одному** (`git sparse-checkout add /Resources/Audio/…/файл.ogg`); каталог целиком может не материализоваться.
- Опасно запускать `git grep` по всему дереву SS14 в частичном клоне: он очень долго подтягивает файлы. Используй `grep -r` по локальному клону AstroNRE.
- Контент SS14 берётся по снимку `910154a7` (для старых генераторов) или по актуальной сборке AstroNRE; следи, чтобы генераторы и код согласовывались по одной версии.
- Тесты, где игрок взаимодействует с предметами: держи объекты рядом с точкой появления (около (3,0.9,3)) и на высоте 0,9, иначе не пройдёт проверка дальности и видимости.

## Восстановление стальной стены на Saltern

Взять стопку стали в активную руку и щёлкнуть ЛКМ по свободной соседней клетке пола. Через 1 с появляются закреплённый Girder и расходуются 2 листа. Второй щелчок по той же клетке со сталью за 2 с закрывает проём обычной стеной и расходует ещё 2 листа. Шаги взяты из SS14 `Recipes/Construction/Graphs/structures/girder.yml` (start → girder → wall). До завершения действия его можно прервать. Для восстановления повреждённой части обшивки требуется пол под проломом.

В Build обычная стена на основном этаже Saltern занимает клетку с герметичными рёбрами. Она участвует в столкновениях, расчёте атмосферы и существующем разрушении стен. Герметизация останавливает утечку через проём, давление восстанавливает атмосферная сеть. Сценарий в штатном наборе gameplay проверяет отмену, оба шага, остаток материала и четыре герметичных ребра.


## Инженерное строительство на Saltern

Открыть Astrocore-Build в VS Code, выбрать `Client + Server` и нажать F5. Также можно запустить `play.cmd`. Лаунчер собирает Build с соседним Astrocore-Engine под Windows, проверяет импорт Saltern, запускает сервер и подключает клиент. После закрытия окна клиента завершается запущенный им сервер.

Меню строительства открывается на G. Взять материал в активную руку, выбрать рецепт и нажать «Разместить», затем щёлкнуть по клетке. Кнопка «Поворот» меняет направление трубы, Esc отменяет размещение. Q выбрасывает предмет из активной руки. Для разных слоёв труб важна точка внутри клетки. В каркасе машины плата определяет необходимые детали и конечный прототип. После выбора другого инструмента можно взаимодействовать с каркасом через E либо щелчком по его клетке. Сварку нужно зажечь и обеспечить топливом. F с RCD в активной руке открывает круговое меню режимов. После выбора режима ЛКМ применяет его к цели. Сложенную надувную секцию ставят щелчком по свободной клетке. Действие Disassemble в контекстном меню складывает перегородку обратно.

Текущая матрица и оставшиеся расхождения с эталоном перечислены в [плане инженерного переноса](ENGINEERING_PORT.md). Данные SS14, графы, поведение и ассеты находятся в Build. Общая смена визуального представления объекта с сохранением его ID реализована в Engine.

Для настройки снятой платы шлюза взять мультитул и взаимодействовать с платой. Выбранные уровни доступа сохраняются на конкретной плате после установки и демонтажа. Импорт Saltern сохраняет ведомственные RSI, плату, сварку, панель и болты. В контекстном меню проводов мультитул даёт Pulse, кусачки дают Cut/Mend. Окно проводов и оставшиеся эффекты импульсов перечислены в матрице инженерного переноса.

Графический режим `Smoke` запускает сервер с `--lobby 0`, чтобы кадр проверки содержал станцию. Обычный `Client + Server` использует штатное лобби. Последние проверенные исходники собраны по коммиту SS14 `31f782a809851c674bd8f86c3aca7c381118c539`.

Проверка 2026-11-15 прошла на Windows. `cargo clippy --locked --offline --workspace --all-targets -- -D warnings` завершился без предупреждений. В полном `cargo test --locked --offline --workspace` прошли 339 тестов, 5 существующих проверок помечены ignored. В локальном Engine прошёл 21 тест `astrocore-render`. Windows/Vulkan smoke с отключённым лобби прошёл, кадр станции просмотрен в `.local/screenshots/engineering-reviewed/frame340.png`. Логи находятся в `.local/logs/engineering-window-*`, `.local/logs/engineering-render-test.log` и `.local/logs/engineering-reviewed-client.*`.

Итог актуального импорта Saltern — 227 дверей, 86 огнезапоров, оба счётчика пропусков равны нулю. Импорт прошёл проверку мира до сохранения. На карте остаются 891 сущность, для которых импортёр не имеет переноса. Полная инженерная приёмка 1:1 остаётся открытой по матрице `ENGINEERING_PORT.md`.

## Провода и механика шлюзов (2026-11-15)

Добавлены `crates/gameplay/src/airlock_wires.rs`, `airlock_doors.rs`, `wires.rs` и клиентские `wires_ui.rs`, `airlock_visuals.rs`. Это логика SS14 в Build. В этом продолжении Engine не менялся. Генератор `scripts/gen_engineering.py` экспортирует Airlock/Door/ApcPowerReceiver, Electrified и Prying с исходными звуками. Учтены обе линии питания, импульсы, отмена таймеров при потере питания, болты, индикаторы, безопасность, задержка, флаги журнала и ИИ. Удар током перед резкой отменяет операцию; изоляция предотвращает удар. Для обычного шлюза без изоляции получается Shock 7 из исходного 7.5 с приведением к целому до коэффициентов.

Открытие и закрытие идут в серверных фазах, отдельно от анимации: по умолчанию изменение проходимости через 0.4 с, завершение ещё через 0.2 с, автозакрытие через 5 с. Проверка прохода повторяется перед смыканием. При отключённой безопасности наносятся исходные Blunt 15, дверь удерживает персонажа 2 с и принудительно открывается обратно. Восстановление питания начинает новую задержку. Монтировка открывает и закрывает обесточенный шлюз; обычная монтировка не вскрывает запитанный. Параметры специальных монтировок читаются из Prying.

Стальная и пласталевая защита внутренней панели проходят монтаж, сварку и обратный разбор. Физическая дверь, плата и доступ сохраняются; исходный GivePrototype возвращает материал в руки с объединением стопок. Промежуточные защитные узлы закрывают доступ к проводам. Все остальные защитные ветви, исходный HighSecDoor и визуальные слои ещё требуют приёмки по матрице.

Поиск зоны шлюза индексируется по ObjectId и обновляется при изменении ревизии мира. Не возвращать полный обход всех authored-объектов для каждого шлюза за тик. `-TraceTicks` в Windows-лаунчере включает необязательную диагностику длительности серверного шага. Компонент `build.airlock_motion` использует двоичные записи по 25 байт и ограничение 16 КиБ протокола; данные отправляются владельцам, в том числе при подключении посреди движения.

В `airlock_wire_tests.rs` десять сценариев: импульсы, удар перед резкой, отмена восстановления безопасности при потере питания, фазы и позднее подключение, автозакрытие после возврата питания, отмена смыкания при опускании болтов, защемление, монтировка, стальная/пласталевая защита, сообщения об отказах без изменения провода.
